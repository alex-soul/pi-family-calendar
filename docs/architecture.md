# Architecture

The application uses SvelteKit 3, Svelte 5, TypeScript and Node.js 24. The supported runtime is one Node process, packaged in one Docker container. SQLite uses Node's built-in `node:sqlite` API; there is no separate database service, ORM or native addon to compile. The kiosk browser runs on the host in the deployed appliance.

## Ownership and boundaries

| Area         | Current owner and behaviour                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Events       | `CalendarProvider` returns a bounded, normalized snapshot. Demo, unconnected and Google read providers exist. Google owns real events.                             |
| Reminders    | `ReminderRepository` is implemented by SQLite. Both interfaces use the same HTTP API and stored rows. This small boundary can later support a real cloud provider. |
| Display      | `/` owns date navigation, readable details and reminder completion. Reminder details support to-do completion; content editing stays on the phone/admin.           |
| Management   | `/admin/reminders` owns reminder forms. It adapts to phone and desktop widths; opt-in LAN access and scoped QR phone forms are available.                          |
| Preferences  | Theme, hidden calendar IDs and preferred main view are per-browser local storage. No data or provider credentials are stored there.                                |
| Installation | Environment configuration sets the source, time zone and data directory. Google OAuth settings and tokens are stored on the server.                                |

The disposable mock established concepts only. This code was built independently from a clean SvelteKit scaffold. Layouts, typography and colour treatments remain open to refinement in this application.

## Dates and display behaviour

Timed events carry offset-bearing instants. All-day events carry calendar dates and an exclusive end date; converting them to UTC midnight would be incorrect. The configured display zone governs day membership. Overlapping events remain separate, vertically stacked cards. All timed events stay in the agenda, including past events. The current/next event is the initial and idle scroll destination for today; browsing older dates retains their events from the start.

Month is a dedicated, close-inspection grid with small event titles and calendar colours. Timed multi-day events are grouped with all-day banners in Day/2/3-day agendas. Their source timestamps remain unchanged. Schedule keeps one entry per occupied date with start time, All day or Until time, plus Day n/total for multi-day entries. Now appears only in today's timed agenda. Day numbers open a Day; overflow expands that date within the Month grid, with Less to collapse. Event rows open details. Schedule is a bounded chronological list with date groups, time ranges and descriptions. It does not establish real availability while using sample data. 7 days is a close-inspection view with smaller cards, starting today on entry (with seven-day paging). The internal saved view key remains week for compatibility. Detailed Day/2-day/3-day views remain the principal appliance layouts.

The browser indexes a bounded event snapshot once per data/filter change. Date formatters are reused. There are no animation loops, external fonts, embedded dashboards or continuous third-party browser calls. Reminder refresh is every 30 seconds while visible, and completion is confirmed by the server before the UI removes an item. The time-only header clock ticks once per second independently of the 30-second refresh. The agenda clock advances while idle. Reset scroll and Return to Today are independent per-browser positive whole-second settings, defaulting to 15 and 60. Blank disables the corresponding timer. Saved legacy Off migrates both to blank; other legacy delays migrate the scroll timer and keep the 60-second date return. Input resets both timers; held pointers, hidden documents, open dialogs and overlay drawers suppress them. Date return retains the chosen view and resets Month to the current month. Menu hiding and all-day collapse remain fixed at 15 seconds; pinned reminder panels do not pause them. Native scroll may also reposition on navigation, filtering/data reload or resizing.

Date swipes use `CalendarStrip` around the event area, leaving header and reminders stationary. Touch/pen starts are accepted only on empty agenda backgrounds in the lower 30% (at most 160px) of each event scroll region, excluding scrollbar edges. CSS keeps vertical panning and pinch zoom native. After horizontal intent locks, adjacent real date windows mount as inert previews and the strip tracks the pointer directly. Column width determines snapping; release velocity projects a short glide, bounded at three dates (three whole weeks in calendar-week). Only after settling does the existing navigation/cache path commit the selected date. Vertical positions are handed to the agenda focus action to prevent auto-scroll jumping during rebase. Neighbors are removed afterward. Cancellation/multitouch restores the starting dates; context/geometry changes cancel safely. Reduced motion omits drag/settle effects. Narrow stacked phone layouts retain button navigation. Month/Schedule, cards, controls, reminder panels and open dialogs/drawers cannot initiate a date swipe. No extra rows, overlay hit targets, continuous animation loop or Google writes are introduced; gestures use the current snapshot, and normal navigation loads coverage if needed at commit.

## Local data

Schema 6 stores saved ToDos/Notes, repeating templates, Note categories, generation days/attempts/receipts, QR grants and settings. Saved items have an ID, title, kind, optional details/date/time, category and integer version; ToDos also have completion state. Updates/deletes use version preconditions and return HTTP 409 on conflicts. All items share the General list. Note categories are separate presentation metadata with colour/icon; deleting a custom category preserves Notes and falls back to General.

SQLite runs in WAL mode with a busy timeout. Newer schemas are rejected. The first upgrade from the legacy reminder model requires an explicitly approved one-time reset, documented in the release notes; legacy reminder history is not migrated. Installations already on schema 6 retain their records without a reset. Google and PIN databases are separate and retained. Notes cannot be completed through the API; changing a completed ToDo into a Note clears completion. Backup verification requires the matching application version; restore with that version before rehearsing an upgrade against the restored copy.

## Development and LAN access boundary

Default Compose is loopback only; compose.lan.yaml optionally publishes a specific LAN address and configures LAN_ORIGIN/PUBLIC_BASE_URL. The direct HTTP launcher derives each request origin from Host using an overwritten protocol header. The hook requires an explicit allowed origin and matching Host, preventing arbitrary Host/DNS-rebinding access. Every mutation requires an exact same-origin Origin header. Application data is no-store, no-referrer and non-embeddable. This is trusted-LAN HTTP, not a public/HTTPS deployment; do not forward the port from the internet.

Optional QR management is disabled by default. It deliberately allows any display user to request an expiring add/edit code; there is no physical-screen authentication. A five-minute one-use scan token is exchanged for a fifteen-minute per-tab session. Add sessions permit multiple creates; Edit sessions permit one successful saved-item or template update or confirmed deletion of the selected stored note, never creation, to-do deletion or admin access. Delete verifies the current type and version; it commits with grant consumption and its own namespaced retry receipt. Turning QR off revokes all grants. The server authorizes every operation separately from PIN sessions, preserving ordinary administrative API gates. Grant hashes, expiry and save receipts live in calendar.sqlite. Save receipts and reminder changes commit atomically; nested reminder operations use savepoints. Failed validation/conflicts retain access and the form; retries return the prior successful result. Codes are rendered locally and carry the token in a URL fragment removed on opening, not query strings. See [QR flow and LAN setup](qr-reminders.md).

## Google read integration

Google is authoritative. The official google-auth-library handles OAuth exchange and token renewal with read-only calendar scope. The browser receives account/calendar metadata, never saved secrets/tokens. Initiation is same-origin POST; callbacks require expiring one-time state, a matching HttpOnly/Lax cookie and PKCE. Sign-in uses a loopback origin. The shipped SSH helper forwards the Pi to a laptop loopback port so consent updates the Pi-owned store; see the Google setup guide. This is not a public callback or LAN pairing flow.

The Pi is the calendar hub. A persistent SQLite mirror stores normalized events, minimal source records, covered date ranges and encrypted per-calendar sync cursors. Credentials use AES-256-GCM with a private local key; event records remain plaintext. Back up the entire data volume including that key. The additive mirror-format v1 migration seeds existing cached windows without changing reminders, PINs or credentials. Rollback should restore a matching pre-upgrade volume and image rather than run an older application against a newer mirror.

A server startup worker runs independently of browsers. It checks each enabled calendar about every 120 seconds, with 25% jitter and exponential failure backoff capped around one hour. The interval is configurable from 60 to 3600 seconds in System. Calendar metadata is refreshed separately every 15 minutes. Concurrent syncs and missing-range reads share one serialized worker; ordinary covered reads never call Google.

Google's unexpanded initial event feed supplies one-off events, recurrence masters and exceptions. Subsequent sync-token requests transfer changes only, with the same query parameters and no incompatible date filters. One-off deltas are applied directly. Changed recurring series are re-expanded by Google across retained coverage, including moved/deleted exceptions. All pages and required instance fetches must succeed before committing the calendar's records and cursor together. HTTP 410 triggers a full replacement using expanded date windows bounded by calendar-year boundaries (at most 366 days each), preserving the old usable data and cursor if any batch fails. Administrative status exposes the active calendar/phase and batch progress without provider payloads. Explicit retries serialize behind existing work and can target one selected calendar; status reads never trigger provider requests. Timeout, interrupted connection, quota, authorization and local update failures have distinct safe messages. See Google's [incremental sync contract](https://developers.google.com/workspace/calendar/api/guides/sync).

The worker maintains coverage from the first day of the previous month through the end of the month twelve months ahead. Past coverage never expires. Older recurrence history imports in 42-day batches, at most one batch per five-second worker tick with a ten-second per-calendar delay, down to the oldest source start (within the supported 1900–2099 browse range). Previously retained future coverage also stays available. Browsing uncovered dates outside the normal horizon asks the Pi to fetch and persist that missing range. No browser receives Google credentials or talks directly to Google. Recurrence expansion always uses Google, avoiding a second RRULE implementation.

Browsers poll the Pi every minute while visible. Fast local reads do not flash a loading message. Temporary failures preserve last-good events and their original sync time; incomplete coverage is reported as importing/unavailable, never confirmed empty. Confirmed permission loss removes locally served data, and deselection/disconnection purges that calendar when no connected account still selects it. This is a synchronized mirror: Google deletions and series changes still apply to historical events, so indefinite retention is not an immutable backup. Date queries are padded one UTC day at either edge and clipped by the display index, preserving all-day exclusive ends and timed offsets.

V1 is deliberately read-only. Google owns event creation, editing and deletion. Two-way sync is not a committed future feature, and the UI has no event-write placeholders. There is no offline write queue or event editor. See [setup and operational limits](google-calendar.md).

## Known Schedule presentation limitation

In 0.2.0, Schedule focus prioritizes an active/upcoming timed event, then a reminder, then a later day before today's all-day event. A focused row can repeat a date heading, and an event-to-reminder divider is added within the same date. These are current behaviours behind the [deferred day-grouping issue](roadmap.md#next-release-schedule-day-grouping-and-initial-scroll), not the desired one-heading/one-group-per-day presentation. The displayed event is above the initial scroll position, not removed from the mirror.

## Compact display and action placement

The header has left-aligned view controls, a centred departure-board split-flap clock, and right-aligned date navigation. A tap/keyboard handle on its divider hides or restores the entire header; it remains reachable while collapsed. Header visibility is saved per browser. Narrow screens wrap view controls onto a second row. The full date is omitted from the header; agenda headings retain weekday/date. Date arrows remain visible whenever the header is open; they do not collapse on idle. A separate, unhighlighted Today button matches the menu button in the bottom-left corner and appears only away from the current day (current month in Month, current week in Week). One tap returns immediately and removes the button. Schedule also detects scrolling away from the current day or next upcoming date when today has no rows. The button stays reachable when the header is hidden. Arrows navigate dates, seven-day blocks or months according to the view; Schedule focuses the chosen date. All-day rows align with timed cards, without a visible label: three rows initially, an unlabelled grip on the separating line for overflow. Tap toggles expansion; drag down expands and drag up collapses. The grip has a narrow background confined to the separator gap; its larger transparent hit area does not obscure the last event. No extra row is allocated to the grip. The strip stays above the timed scroller. Past events remain swipe-accessible; there is no Earlier disclosure. These compact targets require physical touch validation.

Day, 2 days and Schedule have a pinned reminder panel beside the events; other views use date-specific reminder popovers without a side dock. A distinct Reminders header aligns with the agenda headings and contains the Add button. Today shows undated Notes, dated Notes (all-day then timed), undated ToDos, overdue ToDos oldest first, then remaining today's ToDos (all-day then timed). An earlier due time today is overdue too. Notes respect their display window only today. Other selected dates show their own dated saved items or future template previews, without today's undated/overdue backlog. Schedule's pinned panel stays on Today. Timed Notes show a small clock beside the title on every date; details retain the time range. ToDo due time is beside the title; overdue text is red without a separate label. Note category bands match event-edge width, with the category icon before the title. No extra category name or template-preview helper occupies a display row.

Dark replaces Slate with a deeper background and subtle gradients/highlights. Old saved Slate preferences migrate to Dark. No continuous effects or per-card backdrop blurring are used. Preferences, including the idle timeout, remain per-browser.

Month uses four to six rows. At the reference size, five-week months show up to three event lines per day; six-week months show two, keeping the overflow control reachable. Expanding a date grows its row to reveal all event titles, with native Month scrolling when needed. The today marker is a fixed circular highlight with a subtle glossy treatment. Multi-day all-day and timed events use continuous weekly bars with neutral surfaces and calendar-coloured left edges. Bars split at week boundaries with continuation marks and occupy non-overlapping lanes. Exclusive all-day ends and local-time midnight boundaries determine occupied dates. Overflow expands the whole week row so bars stay aligned, then Less collapses it. Single-day recurring instances remain separate entries. Schedule uses compact 36px rows with thin date separators. Near-end user scrolling appends bounded six-week provider windows, preserving the scroll position; a compact button supports empty ranges and retries. The initial window still provides recent history, not infinite backward browsing.

No event writes or direct reminder editors appear on the display. Optional QR management adds a small Plus and a collapsed Scan QR to edit disclosure in details; neither opens an editor on the Pi. Full reminder management belongs to admin; scoped QR phone forms also permit creation/editing and confirmed note deletion. Event writes remain in Google. Display users can complete to-dos and customize local preferences. No admin links or on-screen keyboard are introduced.

Daily, weekday, weekly and monthly templates are supported, with bounded intervals and an optional inclusive end date. Monthly dates clamp to the last day of short months and return to the anchor afterward. A server scheduler creates independent saved items at local midnight, with one 01:00 retry. Generation receipts prevent duplicates, including after generated items are deleted. There is no startup catch-up or backfill. Future dates derive template previews without saving rows; today and past dates use saved items. Template edits affect future previews/generation only. Saved items retain their own edits and completion state, including after template deletion. No cleared-backlog or series-completion model remains.

Rich event descriptions are converted to plain text for display, preserving paragraph breaks, entities and HTTP(S) link destinations. The small entities dependency handles character decoding. The original provider snapshot stays unchanged; output remains escaped Svelte text, never injected HTML.

The rolling 7-day view shares an aligned all-day/multi-day banner grid across its date columns. It reuses the tested weekly span packing, supports overlapping lanes and continuation marks, and keeps timed single-day cards below. Day and 7-day strips initially show three lanes, with the existing tap/drag divider and 15-second idle collapse. Single-day events ending at midnight remain timed cards; grouping uses occupied local dates, not unequal raw timestamp date strings.

Schedule has no heading row; its date label uses month-comma-weekday, with a fixed circular today marker sharing the header selection palette. Month uses that same palette. The 7-day heading shows abbreviated weekday, day and short month on one row, with the weekday emphasized. All-day strip banners retain identical coloured left-edge rounding on start, middle and final dates; continuation chevrons carry the span meaning.

## Management navigation

The display menu contains only display/idle preferences. Calendar visibility lives in the display menu and remains per browser. Administration is a separate full-page /admin portal with Overview, Reminders, Note categories, Google Calendar, Screen, Access, System and About navigation. The display never links there. Legacy /manage URLs redirect to their corresponding protected admin destination.

Optional admin PIN protection uses salted Node scrypt hashes, random server-side sessions (only token hashes persisted), 12-hour absolute expiry and HttpOnly/SameSite=Lax cookies (Secure on HTTPS). Five attempts per minute are allowed installation-wide, persisted across restart; asynchronous derivation is serialized. New PINs use exactly six numeric digits, displayed as six boxes with automatic advance and Enter submission. Existing longer PINs remain usable through an explicit longer-PIN field. PIN changes require the current PIN and revoke all older sessions. Lock revokes this browser's session. No PIN is enabled automatically. Host-only recovery is documented in docs/admin.md.

The request hook authorizes canonical route IDs, covering page data requests and encoded paths. Administrative Google endpoints (including callback), admin endpoints and mutating reminder endpoints require access when PIN protection is enabled. POST /api/reminders/:id/complete is a strict completion-only exception; extra fields are rejected. The existing PATCH endpoint stays administrative, even when used for completion by an older client. Display reads remain public within the existing local-only boundary. Same-origin enforcement applies to every mutation, including unlock and completion. Authentication requests and sessions are separate from Google and reminder databases.

The management list separates ToDos (Active, Completed, Templates) and Notes (Active, Past, Templates). Active excludes templates; Past selects saved Notes dated before the installation's current day. Today's expired Note windows stay Active until tomorrow. Switching reminder type maps Completed/Past. Search and Note category filtering apply to all matching records before bounded response pagination. Active/Templates sort ascending; Completed by completion timestamp descending and Past by date/time descending. Confirmed bulk deletion covers all completed ToDos or past Notes, including filtered-out pages. Past deletion validates a day/record-version revision before committing and preserves templates and generation receipts. Redundant Today/Completed/Templates captions are omitted. The shared responsive editor retains drafts on errors/conflicts.

Google management prioritises accounts and selected calendars, with separate expandable long-term connection guidance and setup/credentials. The shipped guide explains Testing expiry and operator-owned OAuth clients. The app cannot infer Cloud publishing status from its tokens. Management inherits the saved browser theme.

Calendar appearance overrides are installation-wide and keyed by normalized calendar ID, so the same shared calendar uses one name and colour across accounts. Admin validates enabled IDs, names (up to 80 characters) and six-digit hex colours. Overrides are stored separately from Google account metadata in the existing encrypted Google store and applied when snapshots are returned, including cached/stale snapshots. Source metadata and cached events remain unchanged; no Google writes or extra sync are needed. Empty names follow the Google name, and Use Google defaults clears both overrides. Sync, reconnection and temporary deselection preserve overrides.

Dated saved ToDos can be completed on or after their scheduled local day; undated ToDos remain tickable. Future previews cannot be completed. The repository enforces eligibility using the installation time zone at request time. Undo restores that saved item's active state without changing other items. Rejected requests leave versions and data unchanged. Completed details show Done in the header and an aligned Undo completion action below the content.

On narrow admin screens, a top-right hamburger toggles the navigation links, View calendar and (when enabled) Lock admin. Navigation closes after a route change or Escape. Desktop retains its sidebar. Google Accounts & calendars and Calendar appearance use native details sections, collapsed initially.

Schedule forward paging uses /api/calendar?from=YYYY-MM-DD with a fixed 42-day exclusive-end window and the existing 1900-2099 date limits. Each window owns its days, preventing duplicate multi-day rows at boundaries and removing cancelled instances when refreshed. Pages are kept only while Schedule is mounted; changing the base range, source, time zone or calendar selection invalidates pending results and resets the pages. Only user browsing triggers automatic append, one request at a time; empty ranges do not trigger an automatic request loop. Existing rows stay available on failure, with explicit retry. The normal base refresh preserves appended pages; the visible appended window refreshes on scroll or the normal poll, throttled to two minutes. Other appended windows refresh when revisited, not all at once. These browser pages query the persistent Pi mirror; background synchronization and history import are independent of the mounted view. Client rows grow with deliberate forward browsing until leaving Schedule; virtualization and physical Pi memory validation remain future work.

### Native Google event handoff

Event details offer a collapsed QR disclosure, independent of reminder QR grants. The public same-origin POST /api/calendar/event-qr accepts only an event identity already in an enabled calendar's mirror. It returns a locally rendered QR and validated HTTPS Google event UI link (direct links are available outside kiosk mode); arbitrary destinations and unknown events are rejected. Google authenticates the scanning phone and owns all edits. There are no Calendar API writes or extra OAuth scopes.

The normalized optional googleUrl preserves provider htmlLink, including recurring instances. Existing mirrors need no reset/migration: use their exact raw source link if available, otherwise perform a serialized single-event read only when expanded, and persist the link in the existing row. This narrow legacy-link lookup is separate from range loading; covered calendar browsing still never fetches Google. Cache reads survive restart. No recurring master is substituted for an occurrence. Disabled/removed calendars and deleted events cannot issue new codes. A previously scanned link remains subject to Google's access rules.

New-event QR settings live in the existing Google store: disabled by default, with an administrator-selected enabled calendar whose connected account has writer/owner access. Protected /api/admin/event-qr manages them; public status only reports availability. The same display QR endpoint accepts action=add and a validated date, enforces the toggle/default on the server, and creates a Google template URL locally without provider calls. Ordinary Add controls use local-noon bounds (12:00 to 12:00) with explicit IANA zones. Month empty-cell selection requests all-day bounds with an inclusive last selected date; the server validates ordering/date limits and converts to Google exclusive-end dates; src identifies the calendar but does not force a Google account. Removed/inaccessible default calendars suppress Add. Google's phone session owns final permission and saving. Previously scanned Google links cannot be revoked by the Pi toggle.

Day/2/3-day headings have matching circular Add buttons when enabled. Schedule has no event Add controls. Month has no visible Add buttons: empty-cell taps or pointer drags across visible dates open all-day QR drafts. The rolling 7-day header uses the same all-day selection across empty space around dates and all-day banners above its divider. Its date labels have uniform styling; the main header Today control carries today selection. Date numbers still navigate and existing event cards still open details. Pointer cancellation, release outside the grid and Escape cancel selection; keyboard activation creates a single-day draft. Add event dialogs show their heading and QR handoff, just like Add reminder; direct links are suppressed in kiosk mode and selected dates remain encoded in the link. The reminder Plus lives in the Reminders header, clear of the cards. Open QR dialogs pause idle navigation. Event/reminder detail dialogs reserve a snug QR-sized minimum body height and grow for longer content within the viewport with independently scrollable details. A pencil handle slides an overlay from the right without changing dialog dimensions, also at phone widths. QR content mounts on first opening and stays mounted during toggles; closed content is inert. Reduced-motion preferences disable the slide transition. Kiosk mode suppresses outbound Google links, preserving kiosk navigation.

Month and 7 days avoid separate date-context rows. Month's browsed month/year sits to the left of the right-aligned date navigation; first-of-month cells include the short month, independent of header visibility. The rolling view labels its first date and month boundaries inline. Responsive Month context stays within the existing header area and the round today marker belongs to the day number itself.

### Shared Add context

Display Add entry points capture a date context and choose an initial Event or Reminder mode. The existing independent admin permissions control the available modes; multi-day selection excludes Reminder. The QR reminder grant stores only a validated optional default date alongside its existing scope and expiry. It survives redemption/reload and does not constrain user input when saving. Google creation remains a native-template QR handoff.

### Reminder history and local event visibility

Month and agenda views share date-specific reminder popovers. Popovers use available viewport height and scroll only when needed. Notes use category icons and clock markers; saved completed ToDos open details with Undo. Future preview details identify the template in the header, and QR/direct editing uses Edit template. Schedule includes date-specific reminder rows and reminder-only dates. Saved past Notes remain visible in their original calendar dates and in admin Past until deleted.

Event hiding is per browser, event and date and never changes Google. The hidden-events eye opens restoration controls. Month anchors the reminders icon at bottom right with the eye to its left; agenda headings keep their date and action icons together. Event details put Hide for this day in the Edit dock beside the direct-link action. Confirmation replaces the QR content with Cancel/Confirm in the same dock. This local action is available even when Google QR lookup is unavailable. Kiosk mode suppresses outbound direct links.

The header divider's handle remains the show/hide control and is also a status tube: green healthy, red error, neutral unknown/unconfigured. Public `/api/sync-health` returns only status. It incorporates selected-calendar/account errors, missing initial success and prolonged sync silence; the browser also detects stale/failed health requests. Detailed causes and targeted retry remain PIN-protected in admin. It is a synchronization indicator, not a hardware fault detector.

A separate Week view uses Monday–Sunday around the current date on entry, seven-day paging and a faint full-column today highlight. Rolling 7 days remains available and unchanged. Both use aligned all-day strips and shared date/reminder actions, with a single horizontal scroller on narrow screens. Week selection is saved per browser. Clicking a 2/3-day heading opens that exact date in Day.

View-selector changes start at today (the current Monday-Sunday week for Week, current month for Month). Explicit date links still open the requested Day. Display side gutters are equal: 12px at appliance width and 8px on phones; bottom is 8px and top remains unchanged.

The standalone /clock-gallery.html design study offers eight live local-time designs, including full split-flap and seconds-only variants, a selectable header preview, light/dark comparison and pause. It does not alter application preferences. Design 02, Departure board, is selected for the application.

The view selector collapses to the highlighted current-view icon after the shared fixed 15-second idle delay. Normal page interaction reveals the menu but does not expand views. Tapping the selected collapsed icon expands all choices without navigating; choosing a view retains the existing today-based switch behaviour. Nonselected collapsed buttons are inert and hidden from accessibility; keyboard focus transfers to the selected icon if needed. Width/icon transitions take 180ms and leave the centred clock stationary. Header hide/show remains independent. Split-flap tiles animate only on value changes, using the existing one-second clock tick, with no new timers or external assets. Reduced-motion preferences disable both effects.

Date navigation remains visible while the header is open. The separate bottom-left Today control appears when away from today and remains reachable with the header hidden. Header visibility, view-menu collapse and idle date/scroll return are independent.

## Optional kiosk theme control

The host MQTT adapter exposes a Warm/Dark selector for the claimed kiosk browser. An authenticated local application endpoint mediates commands and heartbeat acknowledgements. Ordinary browsers keep independent preferences; absent/stale kiosk heartbeats report unavailable instead of assuming a theme was applied. Host tokens and broker credentials remain outside public source. See [theme integration](../host/theme-setup.md).
