# Architecture

The first build uses SvelteKit 3, Svelte 5, TypeScript and Node.js 24. The supported runtime is one Node process, packaged in one Docker container. SQLite uses Node's built-in `node:sqlite` API; there is no separate database service, ORM or native addon to compile. The kiosk browser will run on the host when the appliance is deployed.

## Ownership and boundaries

| Area         | Current owner and behaviour                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Events       | `CalendarProvider` returns a bounded, normalized snapshot. Demo, unconnected and Google read providers exist. Google will own real events.                         |
| Reminders    | `ReminderRepository` is implemented by SQLite. Both interfaces use the same HTTP API and stored rows. This small boundary can later support a real cloud provider. |
| Display      | `/` owns date navigation, readable details and reminder completion. Reminder details are read-only; to-do completion stays available.                              |
| Management   | `/admin/reminders` owns reminder forms. It adapts to phone and desktop widths; opt-in LAN access and scoped QR phone forms are available.                          |
| Preferences  | Theme, hidden calendar IDs and preferred main view are per-browser local storage. No data or provider credentials are stored there.                                |
| Installation | Environment configuration sets the source, time zone and data directory. Google OAuth settings and tokens are stored on the server.                                |

The disposable mock established concepts only. This code was built independently from a clean SvelteKit scaffold. Layouts, typography and colour treatments remain open to refinement in this application.

## Dates and display behaviour

Timed events carry offset-bearing instants. All-day events carry calendar dates and an exclusive end date; converting them to UTC midnight would be incorrect. The configured display zone governs day membership. Overlapping events remain separate, vertically stacked cards. All timed events stay in the agenda, including past events. The current/next event is the initial and idle scroll destination for today; browsing older dates retains their events from the start.

Month is a dedicated, close-inspection grid with small event titles and calendar colours. Timed multi-day events are grouped with all-day banners in Day/2/3-day agendas. Their source timestamps remain unchanged. Schedule keeps one entry per occupied date with start time, All day or Until time, plus Day n/total for multi-day entries. Now appears only in today's timed agenda. Day numbers open a Day; overflow expands that date within the Month grid, with Less to collapse. Event rows open details. Schedule is a bounded chronological list with date groups, time ranges and descriptions. It does not establish real availability while using sample data. 7 days is a close-inspection view with smaller cards, starting today on entry (with seven-day paging). The internal saved view key remains week for compatibility. Detailed Day/2-day/3-day views remain the principal appliance layouts.

The browser indexes a bounded event snapshot once per data/filter change. Date formatters are reused. There are no animation loops, external fonts, embedded dashboards or continuous third-party browser calls. Reminder refresh is every 30 seconds while visible, and completion is confirmed by the server before the UI removes an item. The time-only header clock ticks once per second independently of the 30-second refresh. The agenda clock advances while idle. Reset scroll and Return to Today are independent per-browser positive whole-second settings, defaulting to 15 and 60. Blank disables the corresponding timer. Saved legacy Off migrates both to blank; other legacy delays migrate the scroll timer and keep the 60-second date return. Input resets both timers; held pointers, hidden documents, open dialogs and overlay drawers suppress them. Date return retains the chosen view and resets Month to the current month. Menu hiding and all-day collapse remain fixed at 15 seconds; pinned reminder panels do not pause them. Native scroll may also reposition on navigation, filtering/data reload or resizing.

## Local data

The schema contains reminder ID, title, list, kind (todo/note), optional details and date, completion timestamp and integer version. Updates/deletes use a version precondition; conflicts return HTTP 409. All reminders use the shared General list. Repeat rules store frequency, interval and optional inclusive end date, with the due date as the series anchor. A separate reminder_occurrences table stores completions by reminder ID and occurrence date; the parent version protects both series edits and occurrence completion/undo.

SQLite runs in WAL mode with a busy timeout. Schema version 4 is recorded using `user_version`; a transactional v1-to-v2 migration adds notes with an empty default, preserving existing rows and versions. The v2-to-v3 transaction adds kind with todo as its default; existing completion states and detail text are preserved. Newer schemas are rejected rather than silently downgraded. Older clients that omit notes or kind on an update preserve those fields. Notes cannot be completed through the API. Converting a completed todo into a note clears its completion state. Rolling back to a pre-v3 application requires a compatible pre-migration backup; no automatic downgrade is provided. Container data lives in a named volume. Backup/export and tested migrations are required before using irreplaceable household data. The v3-to-v4 transaction adds repeat rules and occurrence history, and normalises existing list labels to General without deleting records. Older binaries cannot open v4. Series metadata edits preserve history; changing the schedule or converting to a note clears completion history with an editor warning. Deleting a series cascades to its history.

## Development and LAN access boundary

Default Compose is loopback only; compose.lan.yaml optionally publishes a specific LAN address and configures LAN_ORIGIN/PUBLIC_BASE_URL. The direct HTTP launcher derives each request origin from Host using an overwritten protocol header. The hook requires an explicit allowed origin and matching Host, preventing arbitrary Host/DNS-rebinding access. Every mutation requires an exact same-origin Origin header. Application data is no-store, no-referrer and non-embeddable. This is trusted-LAN HTTP, not a public/HTTPS deployment; do not forward the port from the internet.

Optional QR management is disabled by default. It deliberately allows any display user to request an expiring add/edit code; there is no physical-screen authentication. A five-minute one-use scan token is exchanged for a fifteen-minute per-tab session. Add sessions permit multiple creates; Edit sessions permit one successful whole-reminder/series update or confirmed deletion of the selected stored note, never creation, to-do deletion or admin access. Delete verifies the current type and version; it commits with grant consumption and its own namespaced retry receipt. Turning QR off revokes all grants. The server authorizes every operation separately from PIN sessions, preserving ordinary administrative API gates. Grant hashes, expiry and save receipts live in calendar.sqlite. Save receipts and reminder changes commit atomically; nested reminder operations use savepoints. Failed validation/conflicts retain access and the form; retries return the prior successful result. Codes are rendered locally and carry the token in a URL fragment removed on opening, not query strings. See [QR flow and LAN setup](qr-reminders.md).

## Google read integration

Google is authoritative. The official google-auth-library handles OAuth exchange and token renewal with read-only calendar scope. The browser receives account/calendar metadata, never saved secrets/tokens. Initiation is same-origin POST; callbacks require expiring one-time state, a matching HttpOnly/Lax cookie and PKCE. Sign-in is currently restricted to local-computer origins. LAN pairing and a Pi-friendly callback flow remain separate deployment work.

The Pi is the calendar hub. A persistent SQLite mirror stores normalized events, minimal source records, covered date ranges and encrypted per-calendar sync cursors. Credentials use AES-256-GCM with a private local key; event records remain plaintext. Back up the entire data volume including that key. The additive mirror-format v1 migration seeds existing cached windows without changing reminders, PINs or credentials. Rollback should restore a matching pre-upgrade volume and image rather than run an older application against a newer mirror.

A server startup worker runs independently of browsers. It checks each enabled calendar about every 120 seconds, with 25% jitter and exponential failure backoff capped around one hour. The interval is configurable from 60 to 3600 seconds in System. Calendar metadata is refreshed separately every 15 minutes. Concurrent syncs and missing-range reads share one serialized worker; ordinary covered reads never call Google.

Google's unexpanded initial event feed supplies one-off events, recurrence masters and exceptions. Subsequent sync-token requests transfer changes only, with the same query parameters and no incompatible date filters. One-off deltas are applied directly. Changed recurring series are re-expanded by Google across retained coverage, including moved/deleted exceptions. All pages and required instance fetches must succeed before committing the calendar's records and cursor together. HTTP 410 triggers a full replacement, preserving the old usable data if rebuilding fails. See Google's [incremental sync contract](https://developers.google.com/workspace/calendar/api/guides/sync).

The worker maintains coverage from the first day of the previous month through the end of the month twelve months ahead. Past coverage never expires. Older recurrence history imports in 42-day batches, at most one batch per five-second worker tick with a ten-second per-calendar delay, down to the oldest source start (within the supported 1900–2099 browse range). Previously retained future coverage also stays available. Browsing uncovered dates outside the normal horizon asks the Pi to fetch and persist that missing range. No browser receives Google credentials or talks directly to Google. Recurrence expansion always uses Google, avoiding a second RRULE implementation.

Browsers poll the Pi every minute while visible. Fast local reads do not flash a loading message. Temporary failures preserve last-good events and their original sync time; incomplete coverage is reported as importing/unavailable, never confirmed empty. Confirmed permission loss removes locally served data, and deselection/disconnection purges that calendar when no connected account still selects it. This is a synchronized mirror: Google deletions and series changes still apply to historical events, so indefinite retention is not an immutable backup. Date queries are padded one UTC day at either edge and clipped by the display index, preserving all-day exclusive ends and timed offsets.

V1 is deliberately read-only. Google owns event creation, editing and deletion. Two-way sync is not a committed future feature, and the UI has no event-write placeholders. There is no offline write queue or event editor. See [setup and operational limits](google-calendar.md).

## Compact display and action placement

The header has a left-aligned live clock, centred view controls and right-aligned date navigation. A tap/keyboard handle on its divider hides or restores the entire header; it remains reachable while collapsed. Header visibility is saved per browser. Narrow screens wrap view controls onto a second row. The full date is omitted from the header; agenda headings retain weekday/date. The calendar-shaped Today icon highlights the current day (current month in Month). Arrows navigate dates, seven-day blocks or months according to the view; Schedule focuses the chosen date. All-day rows align with timed cards, without a visible label: three rows initially, an unlabelled grip on the separating line for overflow. Tap toggles expansion; drag down expands and drag up collapses. The grip has a narrow background confined to the separator gap; its larger transparent hit area does not obscure the last event. No extra row is allocated to the grip. The strip stays above the timed scroller. Past events remain swipe-accessible; there is no Earlier disclosure. These compact targets require physical touch validation.

Day, 2 days and Schedule have a solid, titleless reminder panel beside their events; other views retain an overlay dock opened by a side handle; it has no overall heading; active dated items start under Today (or the browsed date) only when present. Undated items have no label and use a separator only when another active group precedes them. Empty-state text and inline completed items are omitted; completed items and undo remain in management. The reminder panel has no footer or controls row; when QR management is enabled a small Plus sits at its bottom right. The display has no link to administration and no Browse all popup; the full list is reached by entering /admin manually. Each group shows todos first, then outlined note cards, with no divider between types. Its count is completed/total for todos whose due date exactly matches the dock date, not the lifetime list size. Day/2-day/3-day use the selected start date; 7 days/Month/Schedule use today. Undated and unfinished older items remain accessible separately but do not inflate the day count. Notes show only on their assigned date or indefinitely if undated; they are never overdue tasks. Past dated notes remain in the full list under Past notes and in their original date view. Future and completed items remain in the full list. Checkboxes complete/undo; text opens read-only details. The editor is shared with the optional scoped /reminder phone flow.

Dark replaces Slate with a deeper background and subtle gradients/highlights. Old saved Slate preferences migrate to Dark. No continuous effects or per-card backdrop blurring are used. Preferences, including the idle timeout, remain per-browser.

Month uses four to six rows. At the reference size, five-week months show up to three event lines per day; six-week months show two, keeping the overflow control reachable. Expanding a date grows its row to reveal all event titles, with native Month scrolling when needed. The today marker is a fixed circular highlight with a subtle glossy treatment. Multi-day all-day and timed events use continuous weekly bars with neutral surfaces and calendar-coloured left edges. Bars split at week boundaries with continuation marks and occupy non-overlapping lanes. Exclusive all-day ends and local-time midnight boundaries determine occupied dates. Overflow expands the whole week row so bars stay aligned, then Less collapses it. Single-day recurring instances remain separate entries. Schedule uses compact 36px rows with thin date separators. Near-end user scrolling appends bounded six-week provider windows, preserving the scroll position; a compact button supports empty ranges and retries. The initial window still provides recent history, not infinite backward browsing.

No event writes or direct reminder editors appear on the display. Optional QR management adds a small Plus and a collapsed Scan QR to edit disclosure in details; neither opens an editor on the Pi. Full reminder management belongs to admin; scoped QR phone forms also permit creation/editing and confirmed note deletion. Event writes remain in Google. Display users can complete to-dos and customize local preferences. No admin links or on-screen keyboard are introduced.

Daily, weekday, weekly and monthly repeats are supported. Daily/weekly/monthly intervals run from 1 to 52; weekdays mean Monday-Friday. Monthly dates clamp to the last day of short months and return to the anchor date afterward. Each occurrence appears on its scheduled date; missed repeats do not accumulate as overdue items. Management shows the next incomplete occurrence and completed history, plus ended series under All. Notes have no completion state. Editing/deleting applies to the whole series; occurrence exceptions are deferred.

Rich event descriptions are converted to plain text for display, preserving paragraph breaks, entities and HTTP(S) link destinations. The small entities dependency handles character decoding. The original provider snapshot stays unchanged; output remains escaped Svelte text, never injected HTML.

The rolling 7-day view shares an aligned all-day/multi-day banner grid across its date columns. It reuses the tested weekly span packing, supports overlapping lanes and continuation marks, and keeps timed single-day cards below. Day and 7-day strips initially show three lanes, with the existing tap/drag divider and 15-second idle collapse. Single-day events ending at midnight remain timed cards; grouping uses occupied local dates, not unequal raw timestamp date strings.

Schedule has no heading row; its date label uses month-comma-weekday, with a fixed circular today marker sharing the header selection palette. Month uses that same palette. The 7-day heading puts day number and abbreviated weekday on one row. All-day strip banners retain identical coloured left-edge rounding on start, middle and final dates; continuation chevrons carry the span meaning.

## Management navigation

The display menu contains only display/idle preferences. Calendar visibility lives in the display menu and remains per browser. Administration is a separate full-page /admin portal with Overview, Reminders, Google Calendar and Access & system navigation. The display never links there. Legacy /manage URLs redirect to their corresponding protected admin destination.

Optional admin PIN protection uses salted Node scrypt hashes, random server-side sessions (only token hashes persisted), 12-hour absolute expiry and HttpOnly/SameSite=Lax cookies (Secure on HTTPS). Five attempts per minute are allowed installation-wide, persisted across restart; asynchronous derivation is serialized. PIN changes require the current PIN and revoke all older sessions. Lock revokes this browser's session. No PIN is enabled automatically. Host-only recovery is documented in docs/admin.md.

The request hook authorizes canonical route IDs, covering page data requests and encoded paths. Administrative Google endpoints (including callback), admin endpoints and mutating reminder endpoints require access when PIN protection is enabled. POST /api/reminders/:id/complete is a strict completion-only exception; extra fields are rejected. The existing PATCH endpoint stays administrative, even when used for completion by an older client. Display reads remain public within the existing local-only boundary. Same-origin enforcement applies to every mutation, including unlock and completion. Authentication requests and sessions are separate from Google and reminder databases.

The management shell provides Reminders/Google Calendar navigation and a return to the display. Reminders start with a searchable list and Active, Completed and All filters, optionally scoped to one list. Date groups distinguish today, overdue to-dos, upcoming items, anytime, past notes and completed items. Active excludes completed items and past dated notes. To-dos have completion/undo; notes do not. Tap text to edit in a dialog; creation/editing/deletion stay on admin. Successful saves use the API's returned version and update the local list without a second request. A failed/stale edit retains its input and offers explicit reload of the saved version. Deletes require confirmation. Recurrence is evaluated from stored local-date rules; no cloud service is needed.

Google management prioritises accounts and selected calendars, with separate expandable long-term connection guidance and setup/credentials. The shipped guide explains Testing expiry and operator-owned OAuth clients. The app cannot infer Cloud publishing status from its tokens. Management inherits the saved browser theme.

Calendar appearance overrides are installation-wide and keyed by normalized calendar ID, so the same shared calendar uses one name and colour across accounts. Admin validates enabled IDs, names (up to 80 characters) and six-digit hex colours. Overrides are stored separately from Google account metadata in the existing encrypted Google store and applied when snapshots are returned, including cached/stale snapshots. Source metadata and cached events remain unchanged; no Google writes or extra sync are needed. Empty names follow the Google name, and Use Google defaults clears both overrides. Sync, reconnection and temporary deselection preserve overrides.

Dated to-dos can only be completed on their scheduled local day; undated Anytime to-dos remain tickable. Repeating reminders use the occurrence date, not the series start or the browsed date. The repository enforces this for both completion endpoints using the configured installation time zone at request time. UI controls use the same eligibility helper; admin refreshes its local day every 30 seconds. Undo remains available for historical corrections. Rejected completion requests do not change versions or data.

On narrow admin screens, a top-right hamburger toggles the navigation links, View calendar and (when enabled) Lock admin. Navigation closes after a route change or Escape. Desktop retains its sidebar. Google Accounts & calendars and Calendar appearance use native details sections, collapsed initially.

Schedule forward paging uses /api/calendar?from=YYYY-MM-DD with a fixed 42-day exclusive-end window and the existing 1900-2099 date limits. Each window owns its days, preventing duplicate multi-day rows at boundaries and removing cancelled instances when refreshed. Pages are kept only while Schedule is mounted; changing the base range, source, time zone or calendar selection invalidates pending results and resets the pages. Only user browsing triggers automatic append, one request at a time; empty ranges do not trigger an automatic request loop. Existing rows stay available on failure, with explicit retry. The normal base refresh preserves appended pages; the visible appended window refreshes on scroll or the normal poll, throttled to two minutes. Other appended windows refresh when revisited, not all at once. These browser pages query the persistent Pi mirror; background synchronization and history import are independent of the mounted view. Client rows grow with deliberate forward browsing until leaving Schedule; virtualization and physical Pi memory validation remain future work.

### Native Google event handoff

Event details offer a collapsed QR disclosure, independent of reminder QR grants. The public same-origin POST /api/calendar/event-qr accepts only an event identity already in an enabled calendar's mirror. It returns a locally rendered QR and validated HTTPS Google event UI link (the display does not render an outbound anchor); arbitrary destinations and unknown events are rejected. Google authenticates the scanning phone and owns all edits. There are no Calendar API writes or extra OAuth scopes.

The normalized optional googleUrl preserves provider htmlLink, including recurring instances. Existing mirrors need no reset/migration: use their exact raw source link if available, otherwise perform a serialized single-event read only when expanded, and persist the link in the existing row. This narrow legacy-link lookup is separate from range loading; covered calendar browsing still never fetches Google. Cache reads survive restart. No recurring master is substituted for an occurrence. Disabled/removed calendars and deleted events cannot issue new codes. A previously scanned link remains subject to Google's access rules.

New-event QR settings live in the existing Google store: disabled by default, with an administrator-selected enabled calendar whose connected account has writer/owner access. Protected /api/admin/event-qr manages them; public status only reports availability. The same display QR endpoint accepts action=add and a validated date, enforces the toggle/default on the server, and creates a Google template URL locally without provider calls. Ordinary Add controls use local-noon bounds (12:00 to 12:00) with explicit IANA zones. Month empty-cell selection requests all-day bounds with an inclusive last selected date; the server validates ordering/date limits and converts to Google exclusive-end dates; src identifies the calendar but does not force a Google account. Removed/inaccessible default calendars suppress Add. Google's phone session owns final permission and saving. Previously scanned Google links cannot be revoked by the Pi toggle.

Day/2/3-day headings have matching circular Add buttons when enabled. Schedule has no event Add controls. Month has no visible Add buttons: empty-cell taps or pointer drags across visible dates open all-day QR drafts. The rolling 7-day header uses the same all-day selection across empty space around dates and all-day banners above its divider. Its date labels have uniform styling; the main header Today control carries today selection. Date numbers still navigate and existing event cards still open details. Pointer cancellation, release outside the grid and Escape cancel selection; keyboard activation creates a single-day draft. Add event dialogs show only their heading and QR, just like Add reminder; selected dates remain encoded in the link. The reminder Plus overlays the top-right corner without reserving a row. Open QR dialogs pause idle navigation. Event/reminder detail dialogs reserve a snug QR-sized minimum body height and grow for longer content within the viewport with independently scrollable details. A pencil handle slides an overlay from the right without changing dialog dimensions, also at phone widths. QR content mounts on first opening and stays mounted during toggles; closed content is inert. Reduced-motion preferences disable the slide transition. The display has no outbound Google link, preserving kiosk navigation.

Month and 7 days avoid separate date-context rows. Month's browsed month/year sits beside the clock; first-of-month cells include the short month, independent of header visibility. The rolling view labels its first date and month boundaries inline. Responsive Month context stays within the existing header area and the round today marker belongs to the day number itself.

### Shared Add context

Display Add entry points capture a date context and choose an initial Event or Reminder mode. The existing independent admin permissions control the available modes; multi-day selection excludes Reminder. The QR reminder grant stores only a validated optional default date alongside its existing scope and expiry. It survives redemption/reload and does not constrain user input when saving. Google creation remains a native-template QR handoff.
