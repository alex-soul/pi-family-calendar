# Architecture

The first build uses SvelteKit 3, Svelte 5, TypeScript and Node.js 24. The supported runtime is one Node process, packaged in one Docker container. SQLite uses Node's built-in `node:sqlite` API; there is no separate database service, ORM or native addon to compile. The kiosk browser will run on the host when the appliance is deployed.

## Ownership and boundaries

| Area         | Current owner and behaviour                                                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Events       | `CalendarProvider` returns a bounded, normalized snapshot. Demo, unconnected and Google read providers exist. Google will own real events.                         |
| Reminders    | `ReminderRepository` is implemented by SQLite. Both interfaces use the same HTTP API and stored rows. This small boundary can later support a real cloud provider. |
| Display      | `/` owns date navigation, readable details and reminder completion. No text-entry forms.                                                                           |
| Management   | `/manage` owns reminder forms. It adapts to phone and desktop widths; real phone/LAN access is deferred until pairing.                                             |
| Preferences  | Theme, hidden calendar IDs and preferred main view are per-browser local storage. No data or provider credentials are stored there.                                |
| Installation | Environment configuration sets the source, time zone and data directory. Google OAuth settings and tokens are stored on the server.                                |

The disposable mock established concepts only. This code was built independently from a clean SvelteKit scaffold. Layouts, typography and colour treatments remain open to refinement in this application.

## Dates and display behaviour

Timed events carry offset-bearing instants. All-day events carry calendar dates and an exclusive end date; converting them to UTC midnight would be incorrect. The configured display zone governs day membership. Overlapping events remain separate, vertically stacked cards. All timed events stay in the agenda, including past events. The current/next event is the initial and idle scroll destination for today; browsing older dates retains their events from the start.

Month is a dedicated, close-inspection grid with small event titles and calendar colours. Timed multi-day events are grouped with all-day banners in Day/2/3-day agendas. Their source timestamps remain unchanged. Schedule keeps one entry per occupied date with start time, All day or Until time, plus Day n/total for multi-day entries. Now appears only in today's timed agenda. Day numbers open a Day; overflow expands that date within the Month grid, with Less to collapse. Event rows open details. Schedule is a bounded chronological list with date groups, time ranges and descriptions. It does not establish real availability while using sample data. 7 days is a close-inspection view with smaller cards, starting today on entry (with seven-day paging). The internal saved view key remains week for compatibility. Detailed Day/2-day/3-day views remain the principal appliance layouts.

The browser indexes a bounded event snapshot once per data/filter change. Date formatters are reused. There are no animation loops, external fonts, embedded dashboards or continuous third-party browser calls. Reminder refresh is every 30 seconds while visible, and completion is confirmed by the server before the UI removes an item. The time-only header clock ticks once per second independently of the 30-second refresh. The agenda clock advances while idle. Reset scroll and Return to Today are independent per-browser positive whole-second settings, defaulting to 15 and 60. Blank disables the corresponding timer. Saved legacy Off migrates both to blank; other legacy delays migrate the scroll timer and keep the 60-second date return. Input resets both timers; held pointers, hidden documents, open dialogs and overlay drawers suppress them. Date return retains the chosen view and resets Month to the current month. Menu hiding and all-day collapse remain fixed at 15 seconds; pinned reminder panels do not pause them. Native scroll may also reposition on navigation, filtering/data reload or resizing.

## Local data

The schema contains reminder ID, title, list, kind (todo/note), optional details and date, completion timestamp and integer version. Updates/deletes use a version precondition; conflicts return HTTP 409. Completion is a state change on a single item, not a recurrence model. List names currently organise visible content and provide no privacy separation.

SQLite runs in WAL mode with a busy timeout. Schema version 3 is recorded using `user_version`; a transactional v1-to-v2 migration adds notes with an empty default, preserving existing rows and versions. The v2-to-v3 transaction adds kind with todo as its default; existing completion states and detail text are preserved. Newer schemas are rejected rather than silently downgraded. Older clients that omit notes or kind on an update preserve those fields. Notes cannot be completed through the API. Converting a completed todo into a note clears its completion state. Rolling back to a pre-v3 application requires a compatible pre-migration backup; no automatic downgrade is provided. Container data lives in a named volume. Backup/export and tested migrations are required before using irreplaceable household data. A future repeating-reminder model must preserve occurrence-specific completion and undo.

## Development access boundary

This build is intentionally loopback-only. The Node launcher binds to 127.0.0.1. The server rejects non-loopback clients unless `LOOPBACK_PROXY=1` is set, which the supplied Compose file uses behind its explicitly loopback-only published port. Do not use that exception with a LAN/public binding or an untrusted reverse proxy.

Mutating requests require an exact same-origin Origin header. Responses disable caching of application data and prevent embedding. These controls are not a substitute for authentication. Device pairing, management authorization, secret storage and safe LAN access are a prerequisite to deployment.

## Google read integration

Google is authoritative. The official google-auth-library handles OAuth exchange and token renewal with read-only calendar scope. The browser receives account/calendar metadata, never saved secrets/tokens. Initiation is same-origin POST; callbacks require expiring one-time state, a matching HttpOnly/Lax cookie and PKCE. Sign-in is currently restricted to local-computer origins. LAN pairing and a Pi-friendly callback flow remain separate deployment work.

A separate Google SQLite store holds encrypted credentials and up to twelve bounded event snapshots. AES-256-GCM uses a locally generated private key file; event cache data remains plaintext. Protect and back up the entire volume, including the key. The repository never contains operator credentials. Multiple accounts may contribute selected calendars; duplicate calendar IDs are fetched/displayed once. Existing reminder storage/schema is untouched.

The display polls silently every minute; a successful window is reused for two minutes. Only foreground date requests show the loading indicator; background failures still surface stale/error warnings. Complete paginated full-window reads expand recurring instances and atomically replace the prior window after all selected calendars succeed. No sync tokens/webhooks yet. This catches moved exceptions and cancellations without accumulating tombstones. Local-date queries are padded one UTC day at each edge, then clipped by the display's date index. All-day exclusive ends and timed offsets are preserved.

Temporary/quota failure serves last-good events with original freshness and a stale warning. Uncached dates show an unavailable message. Confirmed permission/revocation errors invalidate cached windows; removed calendars are dropped from selection. OAuth/setup edits are blocked during sync so in-flight requests cannot resurrect a disconnected account. Account choices and credential refresh survive restart. UI controls distinguish provider selection (installation-wide) from hiding calendars in one browser.

V1 is deliberately read-only. Google owns event creation, editing and deletion. Two-way sync is not a committed future feature, and the UI has no event-write placeholders. There is no offline write queue or event editor. See [setup and operational limits](google-calendar.md).

## Compact display and action placement

The header has a left-aligned live clock, centred view controls and right-aligned date navigation. A tap/keyboard handle on its divider hides or restores the entire header; it remains reachable while collapsed. Header visibility is saved per browser. Narrow screens wrap view controls onto a second row. The full date is omitted from the header; agenda headings retain weekday/date. The calendar-shaped Today icon highlights the current day (current month in Month). Arrows navigate dates, seven-day blocks or months according to the view; Schedule focuses the chosen date. All-day rows align with timed cards, without a visible label: three rows initially, an unlabelled grip on the separating line for overflow. Tap toggles expansion; drag down expands and drag up collapses. The grip has a narrow background confined to the separator gap; its larger transparent hit area does not obscure the last event. No extra row is allocated to the grip. The strip stays above the timed scroller. Past events remain swipe-accessible; there is no Earlier disclosure. These compact targets require physical touch validation.

Day, 2 days and Schedule have a solid, titleless reminder panel beside their events; other views retain an overlay dock opened by a side handle; it has no overall heading; active dated items start under Today (or the browsed date) only when present. Undated items have no label and use a separator only when another active group precedes them. Empty-state text and inline completed items are omitted; completed items and undo remain in All reminders. The reminder panel has no footer or controls row. All reminders, including completed items, is reached through the main menu. Each group shows todos first, then outlined note cards, with no divider between types. Its count is completed/total for todos whose due date exactly matches the dock date, not the lifetime list size. Day/2-day/3-day use the selected start date; 7 days/Month/Schedule use today. Undated and unfinished older items remain accessible separately but do not inflate the day count. Notes show only on their assigned date or indefinitely if undated; they are never overdue tasks. Past dated notes remain in the full list under Past notes and in their original date view. Future and completed items remain in the full list. Checkboxes complete/undo; text opens detail and the management editor link.

Dark replaces Slate with a deeper background and subtle gradients/highlights. Old saved Slate preferences migrate to Dark. No continuous effects or per-card backdrop blurring are used. Preferences, including the idle timeout, remain per-browser.

Month uses four to six rows. At the reference size, five-week months show up to three event lines per day; six-week months show two, keeping the overflow control reachable. Expanding a date grows its row to reveal all event titles, with native Month scrolling when needed. The today marker is a fixed circular highlight with a subtle glossy treatment. Multi-day all-day and timed events use continuous weekly bars with neutral surfaces and calendar-coloured left edges. Bars split at week boundaries with continuation marks and occupy non-overlapping lanes. Exclusive all-day ends and local-time midnight boundaries determine occupied dates. Overflow expands the whole week row so bars stay aligned, then Less collapses it. Single-day recurring instances remain separate entries. Schedule uses compact 36px rows with thin date separators and covers the provider's bounded snapshot, not an infinite history or a claim of complete Google availability.

No event/reminder Add controls appear on the display; reminder creation belongs to management. Event edit/delete placeholders are removed. Reminder recurrence remains an accepted requirement, but no repeating rules are stored and the editor omits non-functional repeat controls. Completion/undo must be modelled per occurrence before recurrence is enabled. Text-entry forms stay on `/manage`.

Rich event descriptions are converted to plain text for display, preserving paragraph breaks, entities and HTTP(S) link destinations. The small entities dependency handles character decoding. The original provider snapshot stays unchanged; output remains escaped Svelte text, never injected HTML.

The rolling 7-day view shares an aligned all-day/multi-day banner grid across its date columns. It reuses the tested weekly span packing, supports overlapping lanes and continuation marks, and keeps timed single-day cards below. Day and 7-day strips initially show three lanes, with the existing tap/drag divider and 15-second idle collapse. Single-day events ending at midnight remain timed cards; grouping uses occupied local dates, not unequal raw timestamp date strings.

Schedule has no heading row; its date label uses month-comma-weekday, with a fixed circular today marker sharing the header selection palette. Month uses that same palette. The 7-day heading puts day number and abbreviated weekday on one row. All-day strip banners retain identical coloured left-edge rounding on start, middle and final dates; continuation chevrons carry the span meaning.

## Management navigation

The display menu separates reminder access, display/idle preferences, per-browser calendar visibility and installation-wide Google connection settings. Browse all keeps a quick completion list on the display; Manage reminders opens `/manage`. Preferences keep their existing per-browser persistence and do not remotely configure another display. On phone-width screens the menu button remains visible rather than disappearing after inactivity.

The management shell provides Reminders/Google Calendar navigation and a return to the display. Reminders start with a searchable list and Active, Completed and All filters, optionally scoped to one list. Date groups distinguish today, overdue to-dos, upcoming items, anytime, past notes and completed items. Active excludes completed items and past dated notes. To-dos have completion/undo; notes do not. Tap text to edit in a dialog; create/edit controls exist only on management. Successful saves use the API's returned version and update the local list without a second request. A failed/stale edit retains its input and offers explicit reload of the saved version. Deletes require confirmation. No new schema, recurrence engine or cloud service is introduced.

Google management prioritises accounts and selected calendars, with separate expandable long-term connection guidance and setup/credentials. The shipped guide explains Testing expiry and operator-owned OAuth clients. The app cannot infer Cloud publishing status from its tokens. Management inherits the saved browser theme.
